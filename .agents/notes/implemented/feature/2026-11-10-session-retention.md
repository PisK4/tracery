# Agent Note: 发布版保留：按完整会话的时间淘汰

Status: implemented

本文承接[容量三门槛与正文回收](../../implemented/architecture/2026-10-20-retention-three-gates.md)的三门槛与正文回收机制、[保留清理的单批边界](../../implemented/bug-fix/2026-11-05-retention-batch-bounds-and-disk-target.md)的批量删除边界，以及[用户设置层](../../implemented/feature/2026-11-09-user-settings-config-tier.md)的设置文件与读写边界。

**取代检查。** 活动树里没有记录持有「按完整会话做时间淘汰」这个决策。容量三门槛持有「元数据保留全部历史，只按预算回收正文」与「raw 会话层只清孤儿代际与封口代际」；本文部分取代这两条，三门槛的 80% / 95% 水位、正文预算回收、来源缺口记录仍由那篇持有。保留清理的单批边界持有有界删除与磁盘回收目标，本文复用，不改。用户设置层持有设置文件的形状、校验与读写 seam，本文只接线「历史与空间」一类，不移动那层的决策。

**已定策略。** 2026-11-10 与 Pis 定下三条：保留以时间为主，期限在设置面板配置；淘汰单位是一条完整会话；常驻后台与随 App 运行都可在设置面板配置，默认常驻后台。本文按这三条设计，不把逐请求正文回收当作历史保留策略。

## Problem

### 现在的保留只回收正文，不决定历史留多久

[容量三门槛](../../implemented/architecture/2026-10-20-retention-three-gates.md)把 `request`、`route_summary`、`request_evidence` 定为长期保留，只按正文预算回收 `block.z`、`skeleton_z` 与 `raw_hook` 副本。这套机制能让采集器在磁盘上活下去，却不能回答用户最直接的问题：这段历史还能留多久。元数据没有自动保留期，`maintain purge-metadata` 是手动命令、按 `day` 删除、不按会话；用户不跑命令，库就只增不减。

### 用户看到的单位是会话，现有删除没有这个边界

页面按 `conv_key` 组织会话卡片，一个会话可以包含多个 `actor`、子代理与多条来源的请求。按天删除会把一条跨越零点的会话切成半条；按正文预算回收只让一部分请求失去正文，元数据、派生结果、标题、会话用量与原始行仍然留在库里。用户看到的是一张卡片里有的请求能读、有的读不到，却找不到一条一致的删除规则。

### 原始会话层与元数据都没有真正的上限

2026-11-10 生产只读快照：

| 项目 | 数值 |
| --- | --- |
| 数据目录 | 11.097 GB / 16 GB（69.36%） |
| 请求 / 会话 | 180,470 / 14,647 |
| `raw_session_event` | 377,074 行、2.37 GB 逻辑载荷；80% 的行超过 7 天，7 天 TTL 删除 0 行 |
| 正文预算 | 6.27 GB / 10 GB：block 1.59、request 2.31、raw_session 2.37、raw_hook 0；可回收只有 3.90 GB |
| 会话年龄 | 0–30 天 14,229 个 / 145,595 笔；30–90 天 418 个 / 34,876 笔；90 天以上 0 |

2026-11-10 的[死带修复](../../implemented/bug-fix/2026-11-10-retention-dead-band-and-cost-run-prune.md)用一次手动 `prune-raw` 清掉 535,016 条未匹配费用行与 170,131 条超期 raw，数据目录回到 11.097 GB。这证明手动维护能救一次，不能成为发布路径。

`raw_session_event` 的当前代际要保留完整原文供增量重放，`sessionGenerationDead` 只把没有游标或指纹已失效的代际判死。生产 377,074 行全部落在当前代际，7 天 TTL 对它们一行也删不掉；它们又计入正文预算，却不在可淘汰集合里。按最近 30 天的请求速率外推，raw_session 单独涨到 9 GB 后，正文预算的降级恢复线永远回不来，准入会永久停在 `metadata_only`。

元数据同样没有上限。架构设计的 95% 最后一档「按天淘汰最旧长期元数据」还没有实现，16 GB 硬上限目前只是一句承诺。[保留清理的单批边界](../../implemented/bug-fix/2026-11-05-retention-batch-bounds-and-disk-target.md)已经承认：单独给磁盘回收加批次解决不了长期元数据占用。

### 自动清理与运行形态还按开发机写死

小时级 `rawPruneTick` 每次只准备 2,000 个候选、给 200 ms 墙钟；生产一次 170,131 行的超期 raw 存量靠手动 `maintain prune-raw` 才清掉。`rawPruneTick` 启动时也不跑，短 uptime 永远追不上到期量。两个容量预算固定为 10 GB / 16 GB，与用户磁盘大小无关，剩余空间只留 256 MiB。保留 tick 的同步事务最长到 2 秒，事件循环 p99 已经到 356.7 ms。桌面外壳只做窗口宿主，不启动、不重启、不监管采集器；软件发布后不能要求用户自己配 launchd、自己跑维护命令。

## Decision

### 1. 保留期以会话的最后活动时间为准

新增用户设置 `retentionDays`，取值 7 / 30 / 90 / 180 / 365 天，默认 30 天。默认取 30 而不是 90，是因为最近 30 天已经有 145,595 笔请求；按同一速率把窗口拉到 90 天约 43 万笔，正文预算、会话原始层与元数据会一起超过 16 GB 上限。30 天在默认预算内留得出余量，用户可以在设置面板改长，面板同时给出占用预估与「可能触发磁盘兜底」的提示。

会话的年龄取该 `conv_key` 下所有请求的 `MAX(started_ms)`，即会话最后一次活动时间，与页面列表的排序依据一致。淘汰条件是这个时间早于 `now - retentionDays × 86,400,000`，按精确时长算，不按自然日边界切。一个会话首笔请求可能在窗口之外，只要最后活动在窗口内，整条会话保留；反过来，一条长期没有新请求的会话整体消失，不留下半条。

标题请求、旁路请求与探针组也是独立的 `conv_key`，按自己的最后活动时间淘汰。跨组绑定的标题请求不跟随主会话删除：绑定是读侧的歧义判定，删除侧复制那套规则容易删多；它会作为旁路卡片在自己的时间到点后消失。`conv_key IS NULL` 的孤立请求不构成会话，按同一截止时间逐行删除；生产当前为 0 条。

以下情况即使过期也先跳过，记一条结构化计数，下一轮再试：

- 有在途请求，或该会话的来源代际还有未提交字节、已观察到未提交字节、处于 `open` / `resumable` 的 `source_gap`；
- 该 `conv_key` 下仍有 `purpose_pending = 1` 的请求，或 `derive_queue.state = 'dirty'`；
- 候选选出后、写事务开始前出现了新的请求，事务内重新计算 `MAX(started_ms)` 后发现已不再过期。

跳过不是静默：`/api/metrics` 给 `retention_pending_skipped` 与最老跳过原因。一个会话如果长期 dirty 或长期有缺口，它不会被删，也不会被误报成已清理。

### 2. 一条完整会话的删除集合

删除以 `conv_key` 为范围，在同一个写事务里完成。下表按层列出对象与守卫；字段级结构以[架构设计的存储模型](../../../../docs/architecture-design.md#存储模型)为准，这里只定删除边界。

| 层 | 删除对象 | 守卫与顺序 |
| --- | --- | --- |
| 请求与证据 | `request`、`request_evidence`、`cost_observation`、`tool_call`、`request_block`、无引用的 `block`、`request_alias`、`otlp_body_ref`、`bg_job`，以及指向被删请求的 `prev_req_id` | 费用观测先按证据键删，再删证据行；别名按 `new_id` 先删；正文块引用删完后只回收无引用的块；仍被其他请求引用的路由摘要与原始路由保留 |
| 派生结果 | 该 `conv_key` 的全部 `derive_queue`、`derive_generation`、`derive_request_result`、`derive_chain_work` / `derive_role_work` / `derive_call_work` / `derive_result_work`、`derive_tool_result` | 按 `conv_key` 与 `generation` 删除；按 `req_id` 再兜一层，避免历史代际留下标题、预览与工具事实 |
| 会话附属 | `session_title`、`session_usage` | 标题按 `conv_key` 删；用量按被删请求的 `session` 删，存在其他存活请求使用同一 `session` 时保留；没有对应请求的孤儿标题与用量按各自的观察时间用同一截止时间清理 |
| 原始层 | `raw_session_event`、`raw_ledger`、`raw_hook`、`pending_hook`、`raw_route` | 会话原文按 `(source_kind, session_id)` 与 `file_generation` 删，只在没有存活请求再引用同一会话或代际时执行；账本与 hook 按 `session` 删且没有存活证据引用；路由在账本与请求都摘掉后删 |
| 审计 | `retention_event`、`purged_conversation` | 每个会话一条事件与一条会话墓碑，写在删除之前 |

不删的东西同样明确：其他会话共享的 block、route_summary、request_evidence；`ingest_issue`、`source_gap`、`source_cursor`、`collector_state`；上游 Agent 的会话文件本身。采集器不改写、不删除用户目录里的原始文件。

删除主干从 `src/maintenance/purge.ts` 抽到共享模块，供维护命令与常驻任务共用，常驻进程不 import CLI。每个会话一个 `store.write` 事务，级联、墓碑与事件一起提交；中途崩溃只会留下完整会话，不会留下半个会话。会话之间 `await` 让出事件循环。一个五千笔请求的会话是一个不可拆的同步单元，耗时会明显高于普通会话；先测 `retention_purge_ms_max` 并告警，不在第一版做「隐藏会话、分块删完」的状态机。

### 3. 会话墓碑阻止来源回放把它重新建出来

本地会话文件被重写、换代或重新解析时，按证据键写的 `purged_evidence` 墓碑对不上新代际，旧请求会复活。新增 `purged_conversation` 表，主键 `conv_key`，记录 `purged_at`、`first_ms`、`last_ms`、`request_count`、`reason` 与 `source_kinds`（该会话被删时存在的证据类型，JSON 数组）。各摄入入口在身份确定之后、写库之前查这张表：调用开始时间早于 `purged_at` 的命中计 `purged_skip`、推进游标，不建行、不合并；晚于 `purged_at` 的调用按新片段建行，旧历史不会回来，但同一会话在删除后恢复时仍能看到新的活动。

自动会话淘汰不写逐证据墓碑。一次淘汰 14,000 个会话会产出几十万条 `purged_evidence`，而会话墓碑一条就够阻断整个会话；逐证据墓碑继续留给 `purge-metadata` 与 `purge-agent` 这些按证据范围工作的路径。来源重置本来就要重新摄入，不写墓碑。`purged_conversation` 每个被删会话一行，按当前会话量一年约六万行，可以长期保留。

`reset-source` 是显式的反悔路径：它删除 `source_kinds` 包含该来源证据类型的会话墓碑，并从头重读。混合来源会话只重新摄入被重置的来源，其他来源的数据仍缺，命令输出要列出这些会话；页面不提供「恢复」按钮，避免把不可逆删除伪装成可撤销。

### 4. 调度、追赶与首次启用

新增 `sessionRetentionTick`，启动时跑一次，之后每小时跑一次。每次从设置读取 `retentionDays` 与启用状态，按最旧优先选出候选会话，逐个在独立事务里删除；单次 tick 给 2 秒墙钟，没删完的留给下一轮。删除后按需跑一次小预算 `shrinkStorage`，空闲页没回收完也留给下一轮。

`rawPruneTick` 改为启动时跑一次，小时 tick 内循环 `pruneRawBounded` 到 1 秒墙钟或 10 轮；仍未清完就 5 分钟后重试，并在指标里置 `raw_prune_backlog`。手动 `maintain prune-raw` 保留，用于一次性大存量，不再是发布后的常规路径。

首次启用不自动删除存量。`retentionConfigured` 默认 `false`，历史与空间页显示预览：将删除多少会话、多少请求、最早与最晚日期、估算字节；用户保存保留期后置 `true`，下一次 tick 才开始删。新安装没有超过 30 天的数据，确认不会造成损失；升级安装的当前库有 418 个 30–90 天会话，直接套默认值会删掉 34,876 笔请求，必须先让用户看见并选择。预览走 `maintain retention-preview --keep-days N` 与读取契约里的具名 `retentionPreview`，只读、不写、不读正文。

### 5. 容量账本拆成可读正文与会话原文

正文预算继续管能回收的正文，但不再把 `raw_session_event` 算进去：

- `readable_body_bytes` = `block.z` + `request.skeleton_z` + `raw_hook` 的 `request_z` / `response_z`。正文预算、正文回收与可淘汰量都用这一项。
- `session_raw_bytes` = `raw_session_event.payload_json`。它随会话保留，由会话淘汰删除，不参与正文回收。
- 其余请求行、证据、路由摘要与派生结果归元数据，由会话淘汰和磁盘兜底约束。

`capacityMeterEvictableBytes` 与正文回收路径保持同一口径：block 与 request 骨架是可淘汰上界；raw_hook 正文在淘汰对应请求时清空，但未关联、按 issue 保留的 hook 正文不算可回收。当前生产 raw_hook 为 0，差异为零。这样 raw_session 再大也不会让 `bodyFull` 成立，准入不会因为不可回收的原始层永久停在 `metadata_only`。`/api/metrics` 增加分层占用，健康页能指出是正文、会话原文还是元数据顶到了水位。

磁盘上限与正文预算从可用空间推导，优先级是：先留系统余量，再保正文预算，最后才是保留期。启动时读取磁盘总量与剩余空间，上限取 `min(16 GB, max(2 GB, 剩余空间 - 5 GB))`，正文预算取 `min(10 GB, 上限 × 0.625)`。剩余空间不足 7 GB 时 2 GB 的下限会吃掉那 5 GB 余量，界面必须同时告警「空间不足，保留期可能无法兑现」。公式落在配置与架构文档，本文只定优先级；设置面板显示实际采用的上限与分层占用，不把水位做成用户开关。

80% 档仍只停正文、记元数据，并明确告诉用户是哪一层顶住了；95% 档才允许最后一招：从最旧的完整会话开始淘汰，至少保留最近 7 天，每个会话写 `retention_event`，`reason='disk_cap'`，界面显示「空间不足，已提前删除 N 个会话」。这是唯一会在保留期内删除会话的路径，必须显式记录，不能悄悄执行。若删到 7 天保护线仍然超过 95%，停止写入并保持告警。

### 6. 原始层与重放

`raw_session_event` 从「7 天 TTL 的原始层」改成「会话的一部分」：保留中的会话保留原文，会话被淘汰时一并删除；没有游标或指纹已失效的孤儿代际、封口代际仍按原规则清理。这一条修改[容量三门槛](../../implemented/architecture/2026-10-20-retention-three-gates.md)里「raw 会话层只清孤儿与封口代际」的表述，也解释了为什么 7 天 TTL 在生产删不掉任何当前代际。

删除会话原文时先收集该会话请求的 `session`、`subagent`、`actor` 与 `sort_key` / 证据里的 `file_generation`，再按 `(source_kind, session_id)` 与 `file_generation` 删除；存在其他存活请求使用同一会话或同一代际时保留。`session_id` 为空或对不上任何请求的原始行不猜归属，留给孤儿代际清理，并记 `raw_session_unmapped` 计数。`raw_ledger`、`raw_hook`、`raw_route`、`raw_otlp_span` / `raw_otlp_log` 不按会话重建；前三个按会话与存活证据守卫删除，OTLP 原文没有会话键，继续按 7 天 TTL 过期。

会话被淘汰后，来源文件仍在，下一次扫描会再次看到它；会话墓碑让每个调用计 `purged_skip` 并推进游标，不重新建行。只有用户显式 `reset-source` 才清墓碑重读。保留中的会话原文完整，重放仍按原路径工作；这是会话级删除相对「按 7 天删原始行」的关键差别。

删除原文后，如果来源游标仍指向存在的文件，把该代际的 `committed_off` 与 `observed_off` 退回到 0，让下一次读取从来源重建解析状态。摄入层在写 raw 之前按解析结果里的 `convKey` 与事件时间检查墓碑：早于 `purged_at` 的事件只推进游标，不写 raw、不建行；晚于 `purged_at` 的事件正常入库。这样恢复的会话从新活动开始，旧原文不会被重写回库，新调用也不会在空状态上解析。重置游标只在代际与单个会话一一对应时执行；多会话共用的 SQLite 代际不重置，按墓碑跳过旧调用，并记 `retention_cursor_reset_skipped`，恢复后的新调用按来源现有的增量语义解析。重置游标会重新读一遍文件，大会话的首次恢复读取会变慢；阶段 1 要测单个最大文件的恢复耗时。

### 7. 设置面板与运行形态

`src/settings.ts` 增加三个字段：`retentionDays`（7 / 30 / 90 / 180 / 365，默认 30）、`retentionConfigured`（默认 `false`）、`runMode`（`always` / `app`，默认 `always`）。历史与空间页从「尚未接线」换成四组内容：

- 保留期分段选择；旁边只放一个 hover / focus 气泡，说明按会话最后活动时间计算、正文仍受空间预算约束。
- 当前占用与最近一次清理：会话数、请求数、分层字节、删除了多少会话；数字来自 `/api/metrics` 与 `retentionPreview`，不在页面里算。
- 自动清理状态：未启用时显示预览与「启用」动作；保存后显示下一次清理时间。正常态不挂装饰性状态条。
- 后台运行方式：桌面宿主且服务安装器可用时显示分段选择，浏览器宿主只读显示当前模式。第一版只实现 macOS：常驻模式装用户级 LaunchAgent（`local.tracery`，`RunAtLoad` + `KeepAlive`），随 App 模式由 Tauri 外壳启动采集器子进程并在退出时优雅停止；Windows / Linux 未支持前不摆可点的开关。

保留期保存后由下一次清理读取 `settings.json` 生效，不需要重启采集器。运行方式的切换归桌面外壳与安装器，采集器只负责启动时追赶；页面不声称已经切换，除非宿主返回成功。首次启用前，面板给备份说明的入口；不自动做全库备份，空间紧张时全库备份会让占用翻倍。设置读写继续走既有 `/api/settings` 与具名读取操作；预览是新增用途，按[读取功能接入规则](../../../../docs/read-feature-rules.md)登记，不新增第二个 fetch 调用点。

### 8. 迁移与落地顺序

schema 升到 v18，只新增 `purged_conversation` 表；现有表、容量计数触发器与 `retention_event` 不动。`maintenance/backup.ts` 的表清单加入新表，`maintain verify` 增加一条「被删会话没有残留请求」的抽查。升级不自动删数据：`retentionConfigured` 保持 `false`，用户在历史与空间页看见预览并保存后才启用。`purge-metadata`、`purge-agent`、`reset-source` 保留，文档说明常规保留由自动会话淘汰承担。

| 阶段 | 交付 | 验收 | 依赖 |
| --- | --- | --- | --- |
| 0 预览 | `maintain retention-preview` 与只读统计；不改库 | 当前库预览出 30 天 / 90 天两档的会话、请求、字节与首末日；不写库 | 无 |
| 1 删除核心 | schema v18、`purged_conversation`、会话删除事务、手动 `maintain retention-apply` | 合成级联与共享守卫测试；生产副本上 apply 后 `maintain verify` 通过 | 阶段 0 |
| 2 自动与设置 | `sessionRetentionTick`、`rawPruneTick` 启动追赶、设置字段与历史与空间页 | 首次启用不删存量；确认后按会话删除；短 uptime 能追平 raw 到期量 | 阶段 1 |
| 3 容量拆分 | 正文 / 会话原文 / 元数据分层计数、磁盘推导、95% 整会话兜底 | raw_session 不再触发 `bodyFull`；95% 只删最旧会话并留事件；合成小磁盘验收 | 阶段 1 |
| 4 运行形态与 soak | macOS LaunchAgent / 子进程两种模式、6–12 个月合成 soak | 两种模式都能启动追赶；soak 不越磁盘上限、不无界增长 | 阶段 2、3 |

先做只读预览，再做手动删除，最后才挂自动调度。顺序的原因是可逆性：预览和副本验证能在不碰生产数据的情况下暴露级联错误，自动调度一旦上线就没有第二次试错机会。

## Consequences

2026-11-10 落地，生产副本预演、生产部署与首次启用均已完成；30 天自动清理在启用当天清完 422 个存量会话，此后按小时执行。与本文原方案相比有五处落地差异：

- **会话与代际索引。** 首次预演在 11 GB 生产副本上单会话最长 38.5 秒，419 个会话总耗时 36 分钟；慢在按 `session`、按 `sort_key` 代际前缀的存活检查逐行全表扫。schema v18 增加 `i_req_session`、`i_req_sort_generation` 与 `i_raw_session_event_generation` 后，同一批 421 个会话总耗时 2 分 53 秒，单会话最长 2.87 秒（冷缓存首会话），其余按请求数近线性。
- **块回收改为批次一次。** `purgeTargetsTx` 不再每个会话全库扫无引用块，只回收本次目标引用过的块；`purgeExpiredSessions` 在一批删完后兜一次全局无引用块清扫。这样既避免每会话 0.25 秒的固定成本，也让 `maintain verify` 的 `dangling_blocks` 保持 0。
- **首次启用追赶。** 一轮没删完（`timed_out` 或 `may_have_more`）时 1 分钟后继续，不等到下一个整点；删完自动停。生产首次启用按 61 轮清完 422 个会话 / 35,219 笔请求，用时 62 分钟；单会话写事务平均 300 毫秒、最大 1.02 秒，准入全程 `normal`。
- **预览字节改为物理口径。** `bytes.readable_body` 从逻辑 `body_bytes` 改为目标会话引用的 `block.z` + `request.skeleton_z` 物理字节，与容量分层同口径；共享块不扣除（生产快照精确独占与按引用统计只差 2 KB），避免扫 34M 行 `request_block` 把预览拖到 11 秒。实测预览 1.2 秒，同一截止时间下预览与实删均为 421 个会话 / 35,155 笔请求。
- **运行方式先只读。** 浏览器宿主下「常驻后台 / 随 App」只显示当前值，不摆不可用的开关；切换要等桌面宿主与安装器，即本文阶段 4。字段已落 `settings.json`，宿主接入后可直接读。

仍未覆盖：桌面/浏览器页面走查、6–12 个月合成 soak、macOS LaunchAgent 安装器与 `runMode` 的实际执行；95% 磁盘兜底尚未在真实库触发。见[验收记录](../../../../docs/acceptance.md#会话保留自动清理启用与首批删除2026-11-10)。

## Alternatives considered

**继续只回收正文，元数据保留全部历史。** 这是当前实现。它能让库在正文预算内滚动，却不能给用户一个可配置的历史期限；元数据、派生结果与原始会话层继续增长，16 GB 硬上限没有可执行的收敛方式。发布版需要回答「留多久」，这条不满足。

**按天删除请求行。** 现有 `purge-metadata` 就是这么做的。跨零点的会话会被切成半条，页面上一张卡片有的请求能读、有的消失；用户无法从删除结果还原会话边界。按完整会话删是用户明确选定的单位。

**按请求删除过期数据。** 同样破坏会话完整性，而且标题、工具配对、子代理谱系与派生结果都要各自补一套级联。整会话删除只处理一个身份，读侧不需要新增「部分会话」状态。

**把 raw_session_event 继续按 7 天 TTL 删。** 当前代际的原文是增量重放的状态来源，删掉旧行后下一次追加会从空状态开始，解析结果会错。生产 80% 的会话行超过 7 天却一行没删，正是这条规则在生效；不能靠调小 TTL 解决。

**淘汰会话时保留 raw 行，等 7 天 TTL 再删。** 用户删了会话，原始正文还留在库里，既不符合保留承诺，也让 raw 层继续占用空间。raw 会话行必须随会话删除。

**把 raw 会话行按独立预算淘汰，不管会话。** 这会把一条仍在保留期内的会话的重放状态删掉，重放与解析都可能出错；删除单位又回到「部分会话」。要么整会话删，要么保留。

**在 80% 档就删最旧会话。** 用户选的是时间保留；80% 应该只停正文并说明原因。提前删会话会把保留期变成一句空话。95% 硬上限仍需要一条收敛路径，所以保留为显式、有事件、有界面提示的最后一招。

**95% 只暂停，不提前删会话。** 暂停能止住增长，但库会永久停在 95%，用户不手动处理就无法恢复采集；发布版没有可执行的收敛路径。保留为最后一招并显式记录，比静默停摆更可解释。

**把磁盘上限直接放大到用户磁盘的一定比例。** 16 GB 是产品上限，不是磁盘比例；直接用 10% 会在 1 TB 盘上放到 100 GB，采集器会长期吃掉用户空间。按剩余空间收缩、保留 5 GB 系统余量，比按总量放大更稳。

**默认保留 90 天或永久。** 当前最近 30 天已有 145,595 笔请求，90 天按同一速率约 43 万笔，默认预算装不下；永久则只能靠 95% 兜底在用户不知情时提前删。默认 30 天并在面板给出预估，用户主动改长，责任边界清楚。

**升级后直接套默认 30 天。** 当前库有 418 个 30–90 天会话、34,876 笔请求，升级即删是意外数据损失。首次只预览、保存后启用，代价是多一步确认，收益是不会在用户没看见的时候删历史。

**用逐证据墓碑阻止回放。** 一次淘汰一万多个会话会写几十万条墓碑，体积和写入都远高于一条会话墓碑；而且本地文件换代后逐证据键本来就对不上。会话墓碑是更小、更直接的守卫。

**把保留期、磁盘上限、raw TTL 全做成设置开关。** 用户只需要决定历史留多久与是否常驻；容量水位、raw TTL、批次是工程事实，摆进设置页会增加心智负担，也无法让用户做出更好的选择。设置层只放保留期与运行方式，其余显示为只读事实。

**在保留任务里用全库 `VACUUM`。** 全库 `VACUUM` 要独占且长时间持锁，在线采集不可行；继续用 `incremental_vacuum` 加 `wal_checkpoint(TRUNCATE)`，空闲页没收完留给下一轮。

**把删除放到独立进程或 Worker。** 删除需要写连接，单写者模型下另起进程要跨进程协调锁，收益只是把同步事务挪走，复杂度远高于按会话分批。先测单会话事务耗时，超过预算再考虑隐藏状态的分块删除。

## Testing

合成数据测试覆盖以下场景，生产副本预演与生产部署复核结果见[验收记录](../../../../docs/acceptance.md#会话保留自动清理启用与首批删除2026-11-10)。尚未执行的检查列在 Consequences 的「仍未覆盖」，不在这里写成已通过。

- **整会话边界**：构造会话 A（最后活动 40 天前，首笔 100 天前）、B（最后活动 20 天前，首笔 100 天前）、C（最后活动 40 天前但 `derive_queue` dirty）。30 天保留期下，A 整条删除，B 整条保留（首笔 100 天前的请求仍在），C 本轮跳过；C 转 clean 后下一轮删除。
- **级联完整**：A 删除后，`request`、`request_evidence`、`cost_observation`、`tool_call`、`request_block`、`derive_*`、`session_title`、`session_usage`、`raw_session_event`、`raw_ledger`、`raw_hook`、`bg_job` 都没有 A 的残留；A 独占的 block 删除，A 与 B 共享的 block、route_summary 与原始路由保留；`maintain verify` 通过。
- **墓碑阻断回放**：删除 A 后，用同一 `conv_key` 的本地会话文件重新摄入 A 的旧调用（开始时间早于 `purged_at`），调用计 `purged_skip`，不建请求、不合并、不覆盖 B；开始时间晚于 `purged_at` 的新调用建行，会话以新片段出现；`purged_conversation` 有且只有 A 一行。
- **恢复解析状态**：删除 A 后向同一来源文件追加一笔新调用，游标从 0 重建；旧调用不重新写 raw、不建行，新调用正常入库且解析状态完整；源的 `source_cursor` 最终回到文件末尾，下一轮不再重复读取。
- **原始层守卫**：A 与 B 共用同一 `session_id` 时，删除 A 不删该 `session_id` 的 raw 行；只有 A 使用的 `file_generation` 与 `session_id` 被删；`session_id` 为空的行留下并计入 `raw_session_unmapped`。
- **容量口径**：raw_session 单独涨到超过正文预算时，`bodyFull` 不成立，准入仍为 `normal`；正文超预算只回收正文；95% 合成小磁盘下，最旧会话被整条删除并写 `reason='disk_cap'` 的事件，最近 7 天会话不动；降到 90% 以下恢复写入。
- **自动追赶**：启动时 `rawPruneTick` 能清掉超过 2,000 行的到期 raw 存量；小时 tick 在 1 秒预算内继续推进，未清完置 `raw_prune_backlog` 并在 5 分钟后重试；`sessionRetentionTick` 在 2 秒预算内按会话删除，未删完下一轮继续，不重复已删会话。
- **首次启用**：`retentionConfigured=false` 时自动任务只预览不删；保存保留期后置 `true`，下一次 tick 才删；预览数字与实际删除数字一致（允许并发新增造成的差额，并记录差额）。
- **生产副本**：11 GB 生产库副本上预览与 `retention-apply --approval-id` 在同一截止时间各删除 421 个会话 / 35,155 笔请求，`maintain verify` 与四源容量对账通过；生产部署、只读复核与首次启用后的存量删除均已完成，见 Consequences。
- **设置与界面**：保留期与运行方式写入 `settings.json`，坏值回退默认并留 issue；中英字典无缺项，浏览器宿主只显示运行方式当前值。页面宽度、键盘与 `prefers-reduced-motion` 走查未执行，见 Consequences。

## Risks

- **删除不可逆。** 用户可能在确认后才意识到某条会话还要用。缓解：默认 30 天、首次只预览、最短 7 天、每个会话留审计事件、设置页明示「删除不可恢复」。不提供页面上的撤销按钮。
- **一个大会话可能阻塞写线程。** 单会话最多 5,496 笔请求（当前生产），整会话事务可能达到数秒。缓解：先测 `retention_purge_ms_max`、最旧优先、小时 tick 分摊；若实测超过预算，再提「隐藏会话 + 分块删完」的状态机，第一版不提前做。
- **会话墓碑长期增长。** 每个被删会话一行，按当前量一年约六万行，体积小但不会自动消失。缓解：接受长期保留；需要清理时另做显式维护命令，不在自动路径里删墓碑，否则会重新引入回放复活。
- **删除后恢复的同一会话只剩新片段。** 会话墓碑按 `purged_at` 放行新调用，但被删的旧历史不会回来。用户在删除后恢复一条本地 Agent 会话时，看到的卡片会从新活动重新开始；设置页的气泡要说明这一点，避免把「会话还在」误解成「历史还在」。
- **raw 原文随会话删除后，来源文件再次被解析。** 会话墓碑能挡住重新建行，但用户显式 `reset-source` 会清墓碑并重读；此时旧 raw 已删，适配器从文件重新解析，能恢复多少取决于来源本身。这条路径要在文档里写清，不把 reset 说成无损。
- **95% 兜底会在保留期内删会话。** 这是硬上限下唯一可行的收敛方式，和「时间为主」有张力。缓解：只在 95% 触发、至少保留 7 天、每个会话写事件、界面明示；80% 只停正文不删会话。用户看到提示后可以缩短保留期或扩容。
- **正文仍可能早于保留期被回收。** 时间保留保证会话与读数在，不保证正文一直在；正文受字节预算约束。设置页的气泡要说明这一点，否则用户会把「保留 30 天」理解成「正文完整 30 天」。
- **动态预算可能比用户预期小。** 小磁盘上 `diskLimit` 会收缩到 2 GB 左右，保留 30 天可能立刻触发兜底。缓解：设置页显示实际上限与分层占用，首次启用前预览会显示「按当前空间无法完整保留 N 天」。
- **运行方式切换依赖桌面宿主与平台。** 第一版只做 macOS；Windows / Linux 的常驻服务没有可靠实现前，页面不摆可点的开关。浏览器用户仍用 `bun run service` 管理，文档要写清。
- **设置 API 形状变化。** 新增三个字段后，旧客户端 POST 会缺字段被拒；页面与服务端同版本发布，pre-1.0 可以接受。坏文件与旧 overrides 继续按默认值回退。
- **跨组标题与旁路卡片残留。** 主会话删除后，绑定的标题请求作为独立旁路卡片留到自己的保留期。这是有意不复制读侧歧义判定；如果用户觉得噪音，另做「标题随主会话」的提案，不在这次删除路径里猜。
- **跨来源身份错并会导致整会话误删。** 删除范围完全依赖 `conv_key`，如果上游把两个真实会话并进一个 `conv_key`，会一起删。缓解：级联测试覆盖多 actor、多来源与共享证据；生产副本先预览；不在删除路径里做新的身份推断。
